## 3. ★H1 / H2 / H3 结论（team-lead 指定专项）

### H1 —— 账号恢复登录返回给 A 的 `phone` 是什么？【结论：安全，未回填 P】

- `AuthFacadeServiceImpl.loginByPassword` 命中恢复路径时，`recovery=true`、`phoneState=RELEASED`（`:124-125`）。
- 组包 `buildLoginVO(user=A, ...)`：`vo.setPhone(userIdentityService.getCurrentPhone(A))`（`:197`）。
- `getCurrentPhone(A)`（`UserIdentityServiceImpl:126-134`）查 `user_identity(user_id=A, type=PHONE)`；**A 的 PHONE 凭据在归属转移时已被 `deleteById(owner.id)` 删除** → 返回 **null**。
- **因此 A 的登录 VO 中 `phone = null`（空），绝不回填 B 当前的手机号 P。不存在数据串号。** `phoneState` 确为 `RELEASED`。✅

### H2 —— B 输入「手机号 P + A 旧密码」会发生什么？【结论：返回 A 的账号；风险中·设计已接受】

- `resolveUserIdByPhonePassword(P, A旧密码)`：候选有序 `[当前持有者 B, 历史持有者 A(released_time DESC)]`。
- B 无 `user_password` 行（微信建号不设密码）→ 跳过；A 命中 → **返回 A 的 userId**。
- 语义：**「密码即凭据」**——A 的旧密码作为 **A 账号的恢复凭据**保留；**不能登录 B、不迁移给 B**（落实 D6/裁决③）。
- **判定**：与架构 C2/C3 及 §A.4.2 一致，属**预期行为**。**可接受性：中风险**，需知晓「P + A 旧密码」两者方可行，且所得仅为 A 自身账号；但衍生「恢复后可直接补绑攻击者手机号 → 接管 A」（见 ISSUE-3）。**未擅自改源码**，仅给出修法建议。

### H3 —— `updatePhoneState` 是否把其它字段写成 NULL？【结论：安全，不会】

- Nacos 共享配置：`mybatis-plus.global-config.db-config.update-strategy: not_null`（快照 `_nacos3.txt:20`、`_nacos_multipart.txt:30`；`_nacos_step2.txt` 同）。
- `User` PO **无任何 `@TableField(updateStrategy=...)`**（grep 全模块 0 命中）；全仓检索**无 ALWAYS / IGNORED**。
- 故 `userMapper.updateById(new User().setId(userId).setPhoneState(state))` 生成 `UPDATE user SET phone_state=? WHERE id=?`，**不会清空 `nickname`/`role`/`status`**。✅
- **明确结论：非灾难性数据损坏。**

## 5. 问题清单（含严重级别）

> 严重级别：**阻断 / 高 / 中 / 低 / 提示**。本轮**无阻断、无高危**。

### ISSUE-1【中】真空闲号并发绑定可能抛死锁（500）而非可重试的 405
- **文件/行**：`user-service/.../service/impl/UserIdentityServiceImpl.java:142-145`（`SELECT ... FOR UPDATE`）与 `:260-263`（`catch (DuplicateKeyException)`）。
- **现象**：手机号**空闲**时，`SELECT ... FOR UPDATE` 命中不存在的键 → 取 **gap lock**；两并发事务的 gap lock 互不冲突 → 双双进入 `INSERT` → 插入意向锁相互等待 → **可能死锁**（`DeadlockLoserDataAccessException`，非 `DuplicateKeyException`）→ 落入 `CommonExceptionAdvice.handleRuntimeException` 兜底返回 **`SERVER_ERROR(500)`**。
- **期望（PRD E4）**：并发失败方「重试或提示」；理想返回可重试的 `PHONE_OCCUPIED(405)`。
- **影响**：**数据一致性不受影响**（唯一键 `uk_type_app_identifier` 保证只有一方持有 P）；仅失败方的错误码/文案不友好。概率与真实并发强度相关，平时极低。
- **修法建议（不改源码，供工程师评估）**：
  1. 将捕获范围扩大到 `org.springframework.dao.DataAccessException`（含 `DeadlockLoserDataAccessException`/`CannotAcquireLockException`）并映射为 `PHONE_OCCUPIED(405)`；或
  2. 空闲分支改用 `INSERT ... ON DUPLICATE KEY` / 捕获后按影响行数判定；或
  3. 对空闲号路径增加一次「重试 1 次」。
- **验证强度**：静态推演（无 DB 无法复现）。

### ISSUE-2【低】幂等分支仍执行一次 UPDATE，与设计「无任何写入」措辞不符
- **文件/行**：`UserIdentityServiceImpl.java:158-162`。
- **现象**：`P` 已属 B 本人时调用 `updatePhoneState(B, BOUND)`，发出一次 `UPDATE`（置为同值，可能顺带刷新 `update_time`）。
- **期望（时序图②/§A.2.3）**：「幂等：直接返回成功，无任何写入」。
- **影响**：功能无副作用，仅与文档措辞有偏差。
- **修法建议**：幂等分支改为「若 `user.phoneState 已是 BOUND` 则跳过 update」。

### ISSUE-3【中·设计已接受】恢复路径存在「旧号+旧密码 → 补绑新号」的账号接管面
- **文件/行**：`AuthFacadeServiceImpl.java:103-130`（恢复登录）、`UserIdentityServiceImpl.java:103-123`（历史候选）。
- **现象**：知晓「P + A 旧密码」者可登录 A，并可立即 `POST /users/auth/phone/bind` 补绑自己控制的手机号 → 等价取得 A 账号的持续控制权。
- **判定**：这是「历史手机号+密码作为恢复凭据」设计的**固有代价**，架构 §A.4.2 / §B.10-③ 已明确接受（否则无 openid 的 A 将被永久锁死）。
- **建议（产品/安全侧，非本轮范围）**：A 在恢复态补绑时增加二次验证（如短信通知原号/保留期冷却）、或发送账号变更通知（P2-4）。

### ISSUE-4【低】legacy `/users/phone/send-code` 发码入口无图形码
- **文件/行**：`user-service/.../controller/PhoneController.java:46-51`。
- **现象**：该端点直连 `SmsService.sendVerifyCode`，**无图形验证码前置**（仅需登录）。PRD P0-4「所有发短信入口前置图形验证码」若按字面执行，此处不满足。
- **判定**：属 §A.7.3 / §B.8 保留的**兼容端点**（Web 修改密码用），且已要求登录。风险低。
- **建议**：明确其为「登录态内部发码」豁免，或后续统一收敛到 `SmsCodeFacade`。

### ISSUE-5【低】恢复态登录 `phoneState` 硬编码 RELEASED 的边界不一致
- **文件/行**：`AuthFacadeServiceImpl.java:122-125`。
- **现象**：`recovery` 判定为「`matchedUserId` ≠ 当前持有者」，此时无条件 `phoneState=RELEASED`，忽略 `user.getPhoneState()`。若 A 早已另绑新号 P2（`phone_state=BOUND`）却仍用旧号 P+密码登录，VO 会 `phone=P2` 且 `phoneState=RELEASED`（前端会误显示「手机号已被释放」横幅）。
- **判定**：边缘场景，与 §A.3.3「恢复匹配→RELEASED」一致，属预期但有轻微 UI 误导。
- **建议**：可改为 `recovery && user.getPhoneState()!=BOUND` 时才算 RELEASED，或保持现状并在产品侧说明。

### 提示（非问题，供产品/文档收口）
- **TPL-1**：PRD §6.2「情况甲/乙」表与验收清单部分条目已被 §B.10-① 裁决作废（统一走 D3），但 PRD 未同步删除，**验收口径存在歧义**，建议产品侧修订 PRD。
