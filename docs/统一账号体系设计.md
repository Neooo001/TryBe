# TryBe 统一账号体系设计（小程序 + Web 双端一套账号）

> ## ⚠️ 本文已作废（历史留档，勿据此开发）
>
> 「双端一套账号」的前提已被推翻。当前实现为 **双账号域拆分**：
> `wx_user`（小程序）与 `web_user`（后台）**两张表、零交集**，手机号在 web 端是账号标识、
> 在小程序端只是可选便利项。绑号硬门禁与「归属转移」仅在 wx 域保留。
>
> **请改读 [`双账号域拆分-上线与回归.md`](./双账号域拆分-上线与回归.md)。**

> 面向场景：小程序走微信一键登录（个人主体，无开放平台、无 unionid、无网页扫码登录），
> Web 端只能手机号注册/登录，两端必须是**同一个账号**。
>
> 本文档先给企业级标准解法，再给 TryBe 可落地的分阶段改造路径。

## 一、根因：你把「人」和「登录凭据」挤在了同一张表

当前 `user` 表（`sql/userService/创建用户表.sql`）把三类东西混在一起：

| 列 | 实质含义 | 问题 |
|---|---|---|
| `id` / `nickname` / `avatar` / `status` / `role` | **人**的属性（主体） | 合理 |
| `phone` + `password` | **一种登录凭据** | 凭据不该长在人身上 |
| `openid` | **另一种登录凭据** | 同上，且 openid 是「用户 × 小程序」维度，不是「用户」维度 |

一旦把凭据平铺成列，"一个人 = 一行"这个不变量就只能靠业务代码去维护，
而登录入口有两个（微信、手机号），两条链路各自 find-or-create，**必然撞车**。

你描述的场景就是这么发生的：

```
t1  Web 端 138**** 注册          →  User A(id=1, phone=138****, openid=NULL)
t2  小程序 wx.login(openid=oXXX) →  按 openid 查不到 → User B(id=2, openid=oXXX, phone=NULL)
t3  B 绑定 138****               →  命中 A → 冲突
```

冲突点在代码里是这一句（**当前直接抛异常，没有出路**）：

```java
// user-service/.../PhoneServiceImpl.java:100-106
User existUser = lambdaQuery().eq(User::getPhone, phone).ne(User::getId, userId).one();
if (existUser != null) {
    throw new BizIllegalException(ErrorCodeEnum.BIZ_ERROR, "该手机号已被其他账号绑定");
}
```

抛完异常之后，用户 B 在衣柜、身形档案里的数据就被锁死在一个登不进去的账号里了。

此外还有两个隐患：

1. **`idx_phone` 是普通索引，不是唯一索引**（`创建用户表.sql:26`）。
   并发注册下同一个手机号能写出两行 —— 你们自己的核查脚本第 21 行其实已经意识到了，
   但没启用。
2. **`PhoneServiceImpl.java:73` 有一个已踩过坑的复现点**：
   `refreshTokenUtil.saveToken(refreshToken, user.getId(), user.getOpenid())` 直接传了可能为
   `null` 的 openid。按 2026-09-21 那轮已经确认的结论，`Redis Hash` 不接受 null 值 →
   **网页注册的账号（openid=NULL）走 `/users/phone/login` 会在下发 token 时抛异常**。
   同一坑在 `CreatorAuthServiceImpl.buildLoginVO` 已经用 `StrUtil.nullToEmpty` 修过，
   这里漏了。

## 二、企业级目标模型：User 1 : N Identity

企业统一账号体系的第一性原理：**User 是"人"，Identity 是"登录方式"。**

```
user（人 / 主体）                      user_identity（凭据 / 登录方式）
┌──────────────────────┐              ┌────────────────────────────────────┐
│ id                   │  1      N    │ id                                 │
│ nickname  avatar     │◄─────────────│ user_id                            │
│ status    role       │              │ identity_type  PHONE / WECHAT_...  │
│ unionid   (预留)      │              │ app_id         openid 必须配 appid  │
│ merged_to_user_id    │              │ identifier     手机号 / openid / ... │
└──────────────────────┘              │ credential     密码哈希（微信侧空）   │
                                      │ verified       是否已验证            │
                                      └────────────────────────────────────┘
                                       UNIQUE(identity_type, app_id, identifier)
```

### 关键设计点（逐条都有企业实践背景）

1. **`openid` 必须带 `app_id`。**
   openid 是「用户 × 单个 appid」维度，同一人在你两个小程序里 openid 不同。
   唯一键写成 `(identity_type, app_id, identifier)` 才不会在扩展第二端时崩掉。
2. **手机号是跨端唯一锚点**（个人开发者尤其，见第四节）。
3. **登录语义从"按手机号找人"改成"按凭据找人"** ——
   先 `unionid` → 再 `openid` → 再 `phone`，任一命中即返回同一个 `user_id`。
4. **密码挂在 Identity 上，不挂在 User 上。**
   同一人可以同时拥有「手机号+密码」和「邮箱+密码」两套密码，密码属于凭据不属于人。
5. **凭据可增删，主体不动。**
   解绑手机号 = 删一行 identity；绑新微信 = 加一行 identity。
   衣柜 / 身形 / 素材全部挂 `user_id`，**永远不需要迁移**。

## 三、企业怎么解决你这个冲突场景

企业里这个场景有专有名词：**账号关联与合并（Account Linking / Account Merge）**。
实践上是三层策略，优先级从高到低。

### 策略 1（治本）：登录即绑定 —— 根本不给 B 产生的机会

这是企业最主流、成本最低的做法，也是**首选**：

> 小程序微信登录成功后，**强制**补齐手机号（`getPhoneNumber` 一键授权或短信验证）。
> 拿到了手机号先查库：
> - 手机号不存在 → 建 User（同时写两条 identity：WECHAT_OPENID + PHONE）
> - 手机号已存在（= 你的 User A）→ **不建新账号**，直接把本次 openid 作为一条新
>   identity 挂到 A 上，返回 A 的 token

用户全程无感知，没有"两个账号"这个中间态，也就没有合并的麻烦。
**企业的注册/登录流程里，"手机号校验"是登录的一部分，不是可选的绑定步骤。**

代价：小程序端必须让用户授权手机号（个人主体小程序**可以**用 `getPhoneNumber`，
但需要小程序已认证/或按现行规则走；若走不通则退化成"短信验证码补手机号"）。

### 策略 2（兜底）：后置合并 —— B 已产生且有资产

当 B 已经存在且已经有衣柜/身形数据，就不能简单丢弃 B。企业标准执行步骤：

| # | 步骤 | 关键细节 |
|---|---|---|
| 1 | **返回冲突态** | 用业务码（HTTP 200 + 特定 code）而非 500；前端弹「该手机号已有账号，是否合并？」 |
| 2 | **二次验证归属** | 必须验证用户对 A 的所有权：短信码 **或** A 的密码。**绝不能仅凭"知道手机号"就合并** —— 否则可恶意吞并他人账号 |
| 3 | **定主从** | 固定规则：**保留手机号账号 A 为主，废弃微信账号 B 为从**。（比"资产多者为主"更好维护，避免出现非确定的合并结果） |
| 4 | **迁移业务资产** | 逐表 `UPDATE t SET user_id = A WHERE user_id = B`；**注意唯一约束冲突**（见下） |
| 5 | **迁移凭据** | 把 B 的 openid identity 的 `user_id` 改到 A；**改之前必须先删掉 A 上同 `(type,app_id)` 的旧行**，否则撞唯一键 |
| 6 | **留墓碑** | B 不物理删除：`merged_to_user_id = A`；B 的 identity 行**保留**。这一步最容易被漏 —— 不保留的话用户下次用老 openid 又重新建出一个新账号，循环复发 |
| 7 | **全会话失效** | 清 A、B 两侧的 RefreshToken 与角色缓存，强制重新登录 |
| 8 | **幂等 + 审计** | 合并日志唯一键 `uk_slave(slave_user_id)` 防重复执行；发短信通知"账号已合并"（合规要求，防钓鱼） |

**第 4 步的真实坑（你的项目正好踩得上）：**
`body_profile` 有 `UNIQUE KEY uk_user_id`（`创建身形档案表.sql:30`），
即"一个用户只能有一条身形档案"。迁移时如果 A 和 B 都有档案，直接 UPDATE 会撞唯一键。
企业做法：**迁移前先探测冲突，冲突时定规则**（保留更新时间更新的 / 保留字段更完整的 /
让用户在弹窗里选），另一条归档到 `*_bak` 表而不是直接删。

`TryBe` 里所有带 `user_id`、合并时必须迁移的表：

```
wardrobe_item        (wardrobe-service)
wardrobe_category    (wardrobe-service，含用户自定义分类)
wardrobe_import_task (wardrobe-service，未 commit 的任务要一起迁)
body_profile         (body-profile-service，⚠️ UNIQUE(user_id)，冲突需特判)
material             (material-service)
material_check_log   (material-service，若有 user_id)
creator_item         (creator-service)
```
`body_profile_material` / `creator_item_model_image` 通过 `profile_id` / `item_id` 间接关联，
迁移父表即可，不用单独动。

### 策略 3（退路）：只拒绝

只有当从账号**完全无资产**时才可接受。也就是你现在的代码行为。
对用户是死路（B 里的数据永远取不出来），只适合早期灰度阶段兜底。

## 四、为什么企业能做，个人开发者做不了：unionid

这是整个问题的**底层硬件差异**，理解了它就理解了你为什么会被卡住。

| | 企业主体 | 个人主体（你的情况） |
|---|---|---|
| 开放平台账号 | ✅ 可注册（300 元/年） | ❌ 需企业/个体户/政府组织 |
| `unionid` | ✅ 同主体下小程序/公众号/App 同一个人 unionid 一致 | ❌ 拿不到 |
| 网页微信扫码登录 | ✅ 开放平台「网站应用」 | ❌ 无法申请 |
| 公众号网页授权 | ✅ 服务号 | ❌ 个人号不支持微信认证 |
| **跨端识别锚点** | **unionid（甚至不需要手机号）** | **只有手机号** |

- `openid` = 用户 × 单个 appid，**互不相通**
- `unionid` = 用户 × 开放平台账号，**同主体全应用一致** → 企业靠它在登录瞬间就知道
  "这个微信用户 = 我库里那个 Web 用户"，连手机号都不用问

**所以：企业能靠 unionid 天然避开你这个冲突；你不能。**
对个人主体项目，**手机号就是唯一可用的跨端锚点** ——
这意味着「手机号唯一性」和「冲突合并逻辑」对你**不是可选项，是刚需**，
必须做到比企业还严格，因为你没有第二道保险。

> 补充：`user` 表预留 `unionid` 列，将来若注册了开放平台账号（个体户主体也可）
> 可以直接启用，不用再改表。

## 五、落到 TryBe：分三阶段改造

毕设不需要一步到位，按下面顺序做，每阶段都能独立跑通。

### 阶段 1（必做，半天工作量）：止血 —— 让冲突"有出路"

对应 SQL 脚本 `sql/userService/统一账号体系改造.sql` 的 `Part 0 ~ Part 1`。

1. 手机号升唯一索引 `uk_phone`（MySQL 唯一索引允许多个 NULL，未绑手机号的账号不受影响）。
   代码侧改为捕获 `DuplicateKeyException`，从 DB 兜底并发。
2. `bind` 不再直接抛异常，改成**返回冲突态**：

```java
// PhoneServiceImpl.bind 改造方向
User exist = lambdaQuery().eq(User::getPhone, phone).ne(User::getId, userId).one();
if (exist != null) {
    // 不抛异常，把冲突事实返回给前端，由前端走"合并确认"弹窗
    throw new BizIllegalException(ErrorCodeEnum.PHONE_OCCUPIED,
            "该手机号已注册，是否将此微信与该账号合并？");
    // 前端凭 PHONE_OCCUPIED 展示确认框 → 调 /users/account/merge/prepare
}
```
3. 顺手修 `PhoneServiceImpl.java:73` 的 null openid（`StrUtil.nullToEmpty`）。

### 阶段 2（推荐，1~2 天）：建模 —— 拆出 `user_identity`

对应 SQL 的 `Part 2 ~ Part 4`。

1. 建 `user_identity` 表；把 `user.phone/password/openid` 迁移进去（脚本 `Part 3`，用 `INSERT IGNORE` 保证可重复执行）。
2. `user` 表加 `unionid`（预留）和 `merged_to_user_id`（墓碑）。
3. Java 侧新增 `UserIdentityService`，登录统一收敛到：

```java
Long resolveUserId(IdentityType type, String appId, String identifier) {
    UserIdentity id = identityMapper.selectOne(...);
    return id == null ? null : id.getUserId();
}
```
4. **兼容期双写**：`user` 旧列先保留，写 identity 时同步写旧列，
   小程序与 Web 都不用改；等两端改造完再删旧列（**不要先删**）。

### 阶段 3（可选，2~3 天）：合并 —— 实现真正的 Account Merge

对应 SQL 的 `Part 5`。

按第三节策略 2 的 8 步实现，核心是一个**不带 `@Transactional` 的编排方法 + 一个纯 DB 事务**

> ⚠️ 按你们既有的硬约定：含 OSS/MQ/大模型等外部交互的方法一律不加 `@Transactional`。
> 合并里会发短信 / 写审计日志，所以拆成：
> `mergeAccount()`（编排，发短信、置缓存失效）→ 调 `mergeAccountInTx()`（纯 DB 事务）。
> 这同时也规避了"长事务占连接"的问题。

对外接口建议（**需登录**，鉴权取 `UserContext`）：

```
POST /users/account/merge/prepare   校验 B 对 A 的所有权（短信码 / A 的密码），返回可合并摘要
POST /users/account/merge/confirm   执行合并，返回主账号 token
```
> ⚠️ 这两个接口**绝不能进网关白名单**（与 `/users/creator/auth/upgrade` 同理）。

## 六、企业还有几个"必须有"的配套（你和企业的真实差距清单）

| # | 机制 | 为什么必须有 |
|---|---|---|
| 1 | **手机号 DB 层唯一索引** | 代码校验挡不住并发，只有唯一索引能 |
| 2 | **换绑冷却期**（换绑后 30 天不可再换/注销） | 防"手机号洗白"：盗号者把手机号换到自己名下再洗白账号 |
| 3 | **注销 ≠ 删除** | 注销后主体进墓碑、identity 全部解绑、**手机号进入冷却期不可复用**。这是解决"运营商回收手机号后新主人登进旧账号"这类经典事故的唯一办法 |
| 4 | **unionid 优先于 openid** | 多端扩展的唯一正确姿势；个人主体暂时拿不到 |
| 5 | **账号审计日志** | 绑定/解绑/合并/换绑全落库。出事故时这是唯一能追溯的东西 |
| 6 | **统一文案防账号枚举** | `CreatorAuthServiceImpl` 已经做对了（"手机号或密码错误"），继续保持 |
